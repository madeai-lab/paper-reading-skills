# Efficient independent reinspection

This execution guidance applies after a genuine source-first review completed in its recorded mode. Read [Review modes](review-modes.md) for revision 2.6 mode-specific scope and continuation fields. Complete Owner source coverage and actual independent evidence remain required. Do not modify a frozen active run to adopt new rules midway.

## Preserve the actual reviewer

Start the initial independent reviewer with clean history, complete source access and no author conclusions. Record the actual host-returned agent/session handle outside the scientific artifacts, together with the source-first checklist, observation notes and last decision paths. Keep the reviewer available while the Owner repairs. Prefer the host's documented resume/message mechanism with that handle; do not create a new reviewer merely because a new decision is required. A new review_id does not require a new agent.

Do not assert that a session cannot be resumed without an actual documented tool limitation or failed attempt. Reuse a live reviewer whenever possible. If a call times out, inspect the existing task and saved outputs before launching another. Never run duplicate reviewers on the same revision. Do not silently retry the same unavailable resume operation.

An independent reviewer who already read the source may see author repairs without losing independence. Fresh/no-history isolation applies at initial appointment; it is not a requirement to erase the reviewer's own knowledge each round. Preserve a compact reviewer-owned checkpoint under reviews/: source hashes, covered unit/claim IDs, source observations and visual evidence paths, latest decision, unresolved requests and remaining work. Write it at meaningful milestones so recovery need not reload the entire transcript. A checkpoint from someone else is attributed prior evidence, never the new reviewer's own viewing.

## Reinspect the changed dependency chain

After completing repairs as one batch, give the same reviewer only the previous decision path, repair note, per-file synchronization reports, changed files/IDs and concise reasons for the changes. Include exact before/after differences when available. Paths to full sources and records remain accessible. Do not resend the entire notebook, prior chat or repeated data contract in every prompt. The reviewer independently determines sufficiency; an Owner's change list cannot limit what the reviewer may inspect.

Compare the full current artifact manifest with the last reviewed version. Use hashes and diffs to find changes, not to establish semantic correctness. Inspect every changed artifact and affected source unit, claim, issue, quantity, target answer, caption, chart and current manual/generated copy. Review historical exceptions and the Owner's per-file dispositions. For unchanged content, the same reviewer may retain its own prior verified coverage without rereading every page. Record the prior review_id, content actually rechecked, unchanged coverage retained and reasons for the dependency boundary. Do not claim a second viewing that did not happen.

Expand reinspection when sources/hashes or scope change, source units are added, changes cannot be bounded, prior evidence is missing, or new findings undermine earlier coverage. A newly appointed reviewer without its own reliable source-first evidence must establish independent coverage; copying another reviewer's checked flags does not meet this requirement. Disclose replacement and its cause. Prevent recurring replacement through lifecycle management rather than dropping independent review.

The new decision covers all requirements of its current review mode, closes every outstanding repair, preserves actual visual evidence and obtains all four fresh snapshot fields after inspection. Revision 2.6 records continuation.previous_review_id, retained_unit_ids and rechecked_unit_ids, with replacement_reason when relevant. For legacy records without these fields, explain retained versus newly inspected coverage in existing disclosures and notes without migrating the frozen schema. Never refresh an old approval or reuse stale snapshot fields.

## Avoid repair and context churn

Have the Owner finish canonical updates, regeneration and report edits before scanning/sealing. Check the actual repairs and dependencies once before dispatch. Keep volatile status/counts in canonical records and link to them from prose; avoid hand-maintained copies of line counts, review-round numbers and changing open-item totals. Do not generate another full mirror of the notebook for each round.

Batch independent local reads/calculations into a compact tool result where practical. Load only relevant record IDs and text ranges; execute stable helpers without printing their full source. Do not dump the entire packet or notebook to answer a narrow field question. Keep original images legible and inspect affected panels; token reduction never justifies substituting captions for pixels. Use the smallest adequate context and avoid full transcript reloads.

Estimate usage from complete per-message or settled CLI usage with clear scope and deduplication; tool heartbeat counters and wall-clock duration are not billing totals. Honor any explicit user cost/token cap. If repeated review rounds keep producing the same synchronization defects, diagnose the generation order and dependencies in one repair batch instead of launching another unchanged review. If the user has imposed no budget, do not invent a resource block or silently declare acceptance; surface continuing cost and the concrete cause of the repeated work.

## Repair transaction and reviewer continuity protocol

Use one repair transaction for all outstanding requests from the latest real decision:

1. Save the pre-repair current-artifact manifest, source hashes, scope revision and actual reviewer handle in an external execution sidecar. Preserve the reviewer's own baseline and evidence. Do not insert execution metadata into the scientific packet or create new schema fields.
2. Map each repair ID to the canonical IDs, affected dependent files and a concrete semantic verification. Make all canonical edits, regenerate once, then update manual report/target/notes. Do not hand-edit generated notebook/index output that the next render will overwrite.
3. Run existing repair scans for every request after all edits. Read the complete discovered file set; batch local searches and inspect relevant surroundings. Share the inspection work across requests with the same affected files, but retain request-specific dispositions and truthful reasons. Never blindly clone scan reports or mark every file checked from a hash alone.
4. Seal readiness with the existing controller. Use its returned assessment and run the read-only checker; classify any remaining errors and fix owner-controlled defects together. Confirm another sync/assessment leaves the scientific content unchanged before dispatch. If output regeneration changes the content, resolve the generation order and rescan before spending another review call. An expected pending-review error is not a reason to fabricate approval.
5. Send one compact delta handoff to the same actual reviewer: previous review ID, outstanding repair IDs, baseline/current manifest paths, changed records/files, affected source locations, owner verification results and evidence paths. These are claims to verify, not prescribed verdicts. The reviewer checks manifest differences, the changed dependency closure and each requested closure against the original evidence, retaining its own verified unchanged coverage. Do not ask it to recreate the complete source-first inventory or read the full paper again for routine repairs.
6. The reviewer writes a new actual decision and fresh snapshot, with its own reviewer checkpoint and actual continuation handle retained for the next transaction. Record which existing coverage was retained and which source locations were reopened. Each initial review retains its actual mode and coverage; incremental repair review must not be described as a new full rereading.

For a host with an Agent resume parameter, use the exact returned handle to resume that reviewer. For a persistent-agent messaging API, keep the reviewer alive and send the delta to it. Inspect the actual available schema; do not guess a parameter or treat a transcript filename as a working resume handle. A new tool call with the same reviewer name is not continuity.

When the user explicitly requires the same reviewer, do not silently replace it with a fresh full-paper reviewer after each repair. If the host cannot actually resume or message the original reviewer, preserve the completed work and report that concrete execution limitation once, with the failed attempt or missing API evidence. Request a supported continuation route rather than spending another full initial review by default. Source/scope changes or evidence invalidation may require expanded verification; explain that reason and preserve all still-valid coverage.
